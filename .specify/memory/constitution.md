# Math Mate 项目章程

## 核心原则

### I. 测试优先 (Test-First) (不可协商)

所有功能开发必须遵循 TDD(测试驱动开发)原则: 编写测试 → 用户批准 → 测试失败 → 然后实现。严格执行红-绿-重构循环。禁止在未编写测试的情况下编写生产代码。

**理由**: 测试优先确保代码质量和可维护性，防止回归，并作为活文档。测试失败是实施前的强制验证步骤。

### II. 集成测试优先 (Integration Tests First) (不可协商)

集成测试优先于单元测试。需要集成测试的重点领域: 新API契约测试、契约变更、服务间通信、共享数据模型、端到端用户流程。单元测试仅用于复杂业务逻辑和算法。

**理由**: 集成测试验证真实交互，捕获接口不匹配和集成问题。优先保证系统级正确性，而非孤立组件的正确性。

### III. 模块化设计 (Modular Design) (不可协商)

每个功能模块必须是自包含的、可独立测试的、有明确单一职责的。模块间通过明确定义的接口通信，禁止紧耦合。每个模块必须有清晰的边界和依赖关系。

**理由**: 模块化设计提高可维护性、可测试性和可扩展性。清晰的边界防止技术债务累积，便于团队并行开发。

### IV. API优先设计 (API-First Design) (不可协商)

所有功能必须通过明确定义的API接口暴露。API设计优先于实现。使用标准RESTful或GraphQL模式，提供OpenAPI/Schema文档。API变更必须版本化，破坏性变更需要迁移计划。

**理由**: API优先确保前后端解耦，支持并行开发，便于集成测试和契约验证。清晰的API契约是系统集成的基础。

### V. 可观测性 (Observability) (不可协商)

所有关键操作必须记录结构化日志。系统必须提供监控指标和健康检查端点。错误必须包含足够的上下文信息用于调试。日志级别必须合理配置，生产环境禁止DEBUG级别日志。

**理由**: 可观测性是生产系统调试和监控的基础。结构化日志和指标支持问题诊断和性能优化。

### VI. 简单性原则 (Simplicity Principle) (不可协商)

从简单开始，遵循YAGNI(You Aren't Gonna Need It)原则。禁止过度抽象和过早优化。复杂性必须得到证明 - 如果选择复杂方案，必须说明为什么简单方案不够。

**理由**: 简单性降低维护成本，提高可理解性。过度设计是技术债务的主要来源。简单方案更容易测试和调试。

## 技术约束

### 架构约束

- **Web应用架构**: 能适应移动端浏览的响应式Web应用
- **前后端分离**: 前端和后端必须通过API通信，禁止直接数据库访问
- **无状态设计**: API服务必须是无状态的，状态存储在数据库或缓存中

### 技术标准

- **API设计**: RESTful API或GraphQL，必须提供OpenAPI/Schema文档
- **数据格式**: JSON作为主要数据交换格式
- **错误处理**: 统一的错误响应格式，包含错误码、消息和上下文
- **版本控制**: API版本化策略，支持向后兼容

### 性能要求

- **响应时间**: API响应时间P95 < 500ms，P99 < 1s
- **并发支持**: 支持至少1000并发用户
- **前端性能**: 首屏加载时间 < 2s，交互响应 < 100ms

### 安全要求

- **输入验证**: 所有用户输入必须验证和清理
- **认证授权**: 实现适当的认证和授权机制
- **数据保护**: 敏感数据必须加密存储和传输
- **安全审计**: 记录所有安全相关操作

## 开发工作流程

### 功能开发流程

1. **规范阶段** (`/speckit.specify`): 创建功能规范，定义用户故事和验收标准
2. **规划阶段** (`/speckit.plan`): 制定技术实施计划，进行章程合规性检查
3. **任务分解** (`/speckit.tasks`): 按用户故事组织任务，确保每个故事可独立实施和测试
4. **实施阶段**: 
   - 先编写集成测试(确保失败)
   - 实现最小可行功能使测试通过
   - 重构代码保持简洁
   - 添加必要的单元测试

### 测试策略

- **集成测试**: 每个用户故事必须有端到端集成测试
- **契约测试**: API变更必须有契约测试验证
- **测试覆盖率**: 关键业务逻辑测试覆盖率 > 80%
- **测试独立性**: 每个测试必须独立运行，不依赖执行顺序

### 代码质量标准

- **代码审查**: 所有代码必须经过审查，验证章程合规性
- **静态分析**: 使用代码检查工具，零警告要求
- **代码风格**: 遵循项目代码风格指南，使用格式化工具
- **文档要求**: 公共API必须有文档，复杂逻辑必须有注释

### 章程合规性检查

- **阶段0研究前**: 必须在阶段0研究前通过章程检查
- **阶段1设计后**: 阶段1设计后重新检查章程合规性
- **PR审查**: 所有PR/审查必须验证合规性，确保符合所有核心原则
- **复杂度证明**: 违反简单性原则的决策必须提供理由

## 治理

### 章程优先级

章程优先于所有其他实践和文档。任何功能开发、技术决策都必须符合本章程规定的核心原则和约束。违反章程的决策必须经过明确批准和文档化。

### 修正程序

章程的修正需要:
1. **文档化**: 明确说明修正原因和影响范围
2. **技术评审**: 需要技术负责人或架构师评审
3. **批准**: 需要项目负责人或核心团队批准
4. **版本控制**: 遵循语义版本控制规则
5. **迁移计划**: 如有破坏性变更，需要提供迁移计划

### 版本控制策略

- **MAJOR(主版本)**: 向后不兼容的原则删除或重新定义
- **MINOR(次版本)**: 新原则/部分添加或实质性扩展指导
- **PATCH(补丁版本)**: 澄清、措辞、拼写错误修复、非语义优化

### 合规审查

- 所有PR/审查必须验证章程合规性
- 复杂性必须得到证明(如违反简单性原则)
- 测试覆盖率必须满足要求
- API变更必须符合API优先原则
- 使用 `.specify/memory/project-description.md` 了解业务上下文，但技术决策以本章程为准
