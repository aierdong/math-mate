# Math Mate 项目章程

## 核心原则 (不可协商)

### 测试优先
所有功能开发遵循TDD：编写测试 → 验证失败 → 实现功能 → 测试通过。禁止在无测试情况下编写生产代码。

### 集成测试优先
优先编写集成测试验证系统级交互，单元测试仅用于复杂算法。

### 模块化设计
每个模块自包含、单一职责，通过明确接口通信。禁止紧耦合。

### API优先设计
所有功能通过标准API接口暴露，提供OpenAPI文档。API变更必须版本化。

### 可观测性
结构化日志、监控指标、健康检查。错误包含调试上下文。

### 简单性原则
遵循YAGNI，避免过度设计。复杂性必须有充分理由。

## 技术约束

- **响应式Web应用**: 适配移动端浏览
- **前后端分离**: 仅通过API通信，无直接数据库访问
- **API标准**: RESTful API，提供OpenAPI文档
- **数据格式**: JSON标准格式
- **性能目标**: P95响应时间 < 500ms，支持1000+并发
- **安全要求**: 输入验证、认证授权、数据加密

## 开发流程

1. **规范** (`/speckit.specify`): 定义用户故事和验收标准
2. **规划** (`/speckit.plan`): 技术实施计划 + 章程合规检查
3. **任务分解** (`/speckit.tasks`): 按用户故事组织任务
4. **实施**: TDD循环（测试→实现→重构）+ 集成测试优先

### 测试策略
- 每个用户故事需端到端集成测试
- API变更必须有契约测试
- 测试覆盖率 > 80%，零警告代码质量标准

### 章程合规性检查

- **阶段0研究前**: 必须在阶段0研究前通过章程检查
- **阶段1设计后**: 阶段1设计后重新检查章程合规性
- **PR审查**: 所有PR/审查必须验证合规性，确保符合所有核心原则
- **复杂度证明**: 违反简单性原则的决策必须提供理由

## 合规审查

- **所有PR必须验证章程合规性**
- **复杂性必须有充分理由**（违反简单性原则需证明）
- **测试覆盖率 > 80%**
- **API变更符合API优先原则**

**章程优先级最高**，技术决策以此为准。
